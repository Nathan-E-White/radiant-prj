Radiant CI · Lesson 2 · 15 minutes

Run expensive tests only when the change warrants them

The technique is not “skip CI.” It is to classify the change, run the relevant checks, and let one cheap, dependable gate report the outcome.

The design: classifier, workers, gate

1. changesTurns the diff into named booleans.
2. workersRun only if their boolean—or a shared dependency—is true.
3. verifyAlways concludes and fails for failed applicable workers.

The classifier is deliberately conservative. When uncertain, include the heavyweight check. A false positive costs runner time; a false negative creates an untested merge.

Choose Radiant’s first path groups

Start coarse. Radiant’s current expensive groups are Docker packaging, Go integration tests, and the dataplane/Iceberg suite. The following groups make a frontend component change cheap while treating shared build files as an “all relevant checks” signal.

jobs:
  changes:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
    outputs:
      backend: ${{ steps.filter.outputs.backend }}
      docker:  ${{ steps.filter.outputs.docker }}
      infra:   ${{ steps.filter.outputs.infra }}
      shared:  ${{ steps.filter.outputs.shared }}
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - id: filter
        uses: dorny/paths-filter@v3
        with:
          filters: |
            backend:
              - 'backend/**'
              - 'lib/iceberg-go/**'
              - 'workers/scada-standins/**'
              - 'workers/simops-generator/**'
            docker:
              - 'Dockerfile'
              - 'worker.Dockerfile'
              - 'docker-bake.hcl'
              - 'docker-compose.yml'
              - 'workers/**'
              - 'scripts/docker-**'
            infra:
              - 'infra/**'
              - 'deploy/**'
            shared:
              - '.github/workflows/**'
              - 'package.json'
              - 'bun.lock'
              - 'backend/slurm-gateway/go.mod'
              - 'backend/slurm-gateway/go.sum'

Interpret the groups as test ownership

These are not a taxonomy of the repository. They are the list of files that can invalidate a particular test’s conclusion. Keep them close to the jobs they govern and tighten them only with evidence.

Make workers conditional

A fast job should run on every PR. A heavyweight job runs when its own area or a shared dependency changes. Give the jobs distinct names; only the final job retains the required verify context.

  fast:
    needs: changes
    runs-on: ubuntu-latest
    steps:
      # checkout, Bun, install, frontend/repository/doc checks

  backend:
    needs: changes
    if: >-
      needs.changes.outputs.backend == 'true' ||
      needs.changes.outputs.shared == 'true'
    runs-on: ubuntu-latest
    services: { postgres: ... }
    steps:
      # checkout, Go, Bun, backend:test, backend:dataplane:test

  docker:
    needs: changes
    if: >-
      needs.changes.outputs.docker == 'true' ||
      needs.changes.outputs.shared == 'true'
    runs-on: ubuntu-latest
    steps:
      # checkout, Buildx, GHCR login, docker:packaging:verify

An irrelevant job is shown as skipped, which is the desired result. It is not a silent success: the final gate knows that it was not applicable.

Preserve the required gate

Radiant’s ruleset requires the context verify. Make it a small aggregator that always runs after all workers. It accepts only success or skipped from optional workers; cancellation or failure blocks the merge.

  verify:
    name: verify
    needs: [fast, backend, docker, infra]
    if: ${{ always() }}
    runs-on: ubuntu-latest
    steps:
      - name: Enforce applicable CI jobs
        env:
          FAST:    ${{ needs.fast.result }}
          BACKEND: ${{ needs.backend.result }}
          DOCKER:  ${{ needs.docker.result }}
          INFRA:   ${{ needs.infra.result }}
        run: |
          test "$FAST" = success
          for result in "$BACKEND" "$DOCKER" "$INFRA"; do
            test "$result" = success -o "$result" = skipped
          done

The sequencing rule

Do this in one PR after the duplicate-trigger fix, not as a collection of unrelated workflow edits. First prove that verify still appears and passes for a frontend-only change, a backend change, and a Docker/build-file change. Then refine path groups from the evidence.

Retrieval practice

Classify these without looking back

One real-world action

Before writing this workflow, write down three representative files: one frontend component, one Go backend file, and one Dockerfile. For each, state which worker jobs must run and why. Those three examples become your first review test cases.
