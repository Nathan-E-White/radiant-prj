Stop duplicate CI without weakening the gate

Your immediate win is to make a PR commit produce one expensive verification, not two—while keeping main protected.

What the repository does today

.github/workflows/ci.yml has both an unrestricted push: trigger and pull_request:. A commit pushed to a feature branch with an open PR therefore starts two readiness-console-ci / verify runs. Each one currently runs Docker packaging, integration tests, and the dataplane/Iceberg suite.

Feature-branch pushmatches unrestricted push
Open PRalso matches pull_request
Two full runssame SHA, twice the spend

The first safe edit

Run PR validation for PRs, and run the full workflow again only once the change reaches main. Also cancel a run that has been made obsolete by a newer commit in the same PR.

on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: readiness-console-${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true

Why this is safe

The PR still gets one full check. After merge, main still gets a check. The only removed work is the duplicate feature-branch push run.

The non-obvious constraint

Radiant’s active main-hygiene ruleset requires the status context named verify. That is your contract with GitHub’s merge gate.

Do not add on.pull_request.paths to this required workflow

If GitHub skips a required workflow through event-level path filtering, its check remains pending and the PR cannot merge. Use path detection inside an always-triggered workflow instead. Make heavyweight jobs conditional; retain a final, always-running verify job.

One real-world action

Open a recent PR’s Checks tab. Confirm that the same commit SHA has both readiness-console-ci / verify (pull_request) and readiness-console-ci / verify (push). After the trigger change lands, use the same comparison to prove the duplicate has disappeared.
