# SimOps Runtime Binding Research

| Scope | Primary-source constraints relevant to Issue #129's Runtime Binding rule |

## Purpose and method

This note distinguishes what Docker Engine and Kubernetes document about
external workload identity and lifecycle from Radiant's proposed policy. It
uses first-party documentation and does not define an adapter interface or
claim that either platform provides workload migration between providers.

In this note, **Runtime Binding** means the repository policy proposed for a
SimOps Run: the runtime adapter selected at creation remains the one used to
launch, observe, stop, clean up, and reconcile that Run.

## Source-backed constraints

### Docker Engine has an Engine-local container identity and lifecycle

- Docker separates container creation from start: `POST /containers/create`
  creates a container and returns its Engine-assigned `Id`; `POST
  /containers/{id}/start` starts that identified container. The optional
  `name` is a Docker Engine name, not a portable execution identity.
  [Docker Engine API v1.51](https://docs.docker.com/reference/api/engine/version/v1.51/)
  and its [OpenAPI specification](https://docs.docker.com/reference/api/engine/version/v1.51.yaml)
  define those distinct operations and the returned ID.
- Inspection, stop, and removal all address a container by Docker's `id` or
  `name`. Stop and remove are distinct operations, with stop allowing a
  timeout and removal optionally forcing deletion. The source therefore
  describes control of an existing Docker Engine resource, not transfer of
  its process, container filesystem, network attachment, or ID to Kubernetes.
  [Docker Engine API v1.51](https://docs.docker.com/reference/api/engine/version/v1.51/)
  and [OpenAPI specification](https://docs.docker.com/reference/api/engine/version/v1.51.yaml).
- Docker labels may be set at creation and used as metadata for lookup. They
  can support reconciliation of a known Run, but labels do not turn a
  container ID into a Kubernetes object identity.
  [Docker Engine API v1.51](https://docs.docker.com/reference/api/engine/version/v1.51/).
- A container runs as an isolated process with its own filesystem, networking,
  and process tree. Its writable layer is unique to that container and is
  destroyed with it; persistent state requires an explicit volume or bind
  mount. This makes any application-level handoff a separate state-transfer
  design, rather than a property of `start`, `stop`, or `remove`.
  [Docker: Running containers](https://docs.docker.com/engine/containers/run/)
  and [Docker: Storage](https://docs.docker.com/engine/storage/).

### Kubernetes Job and Pod identity are cluster-local and controller-shaped

- Kubernetes distinguishes an object's human-readable name from its UID. A
  UID is generated by Kubernetes, identifies one object across its lifetime,
  and is not reusable; deleting and recreating an object with the same name
  produces a different UID. [Object Names and IDs](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/).
- A Job is a controller workload: it creates one or more Pods and tracks
  completion or failure under its own configured semantics. Job identity is
  distinct from the identities and lifecycles of its Pods.
  [Kubernetes Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/)
  and the [Job v1 API reference](https://kubernetes.io/docs/reference/kubernetes-api/workload-resources/job-v1/).
- Pod phase is a high-level summary, deliberately not a comprehensive state
  machine; Pod conditions and container states provide further evidence.
  Kubernetes schedules a Pod once to a node; it runs there until it stops or
  terminates. A replacement is a new near-identical Pod with a different UID,
  not the old Pod relocated to another node. [Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)
  and [Object Names and IDs](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/).
- When a Job's Pod fails, the Job controller starts a new Pod. Kubernetes
  explicitly requires applications to tolerate restart in that new Pod,
  including temporary files, locks, and incomplete output. This is
  replacement semantics, not continuation of the failed Pod's execution.
  [Kubernetes Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/).
- Kubernetes deletion governs Kubernetes-owned objects and their dependents.
  Cascading deletion may be background, foreground, or orphan propagation;
  it is not a protocol for handing execution to Docker Engine.
  [Cascading deletion](https://kubernetes.io/docs/tasks/administer-cluster/use-cascading-deletion/).

### Consequence: re-homing is a new launch, not adapter recovery

The sources describe provider-local identifiers, provider-local lifecycle
operations, and distinct execution models: one Engine container versus a Job
controller and its Pods. **Inference:** neither documented lifecycle offers
an identity-preserving operation that moves a running workload from Docker
Engine to Kubernetes or the reverse. A controller can create a new workload
from equivalent input on another provider, but that is a new external
execution record, not recovery of the original record. Application-level
checkpoint or state transfer may be designed separately; it does not make the
new runtime resource the original provider's execution identity.

## Repository decision for Issue #129 (not an external-source claim)

Radiant will not support container-provider migration for an existing SimOps
Run. It will use **Runtime Binding** as the canonical term for the adapter
selected when that Run is created. Lifecycle Reconciliation observes and
recovers through that recorded adapter only. If a workload must run on a
different provider, the control plane creates a new SimOps Run with a new
Runtime Binding; it does not treat a fresh Docker container or Kubernetes Job
as the prior Run's continued execution.

This preserves truthful external identity, prevents a timeout or missing
resource from becoming a duplicate-workload launch, and leaves the control
plane authoritative for SimOps Run outcome under ADR-0010.

## Design implications

- Persist the Runtime Binding with the SimOps Run before external launch.
- Reconcile unknown starts through the bound adapter first, using deterministic
  Run/worker identity metadata; launch again only after absence is proved.
- Treat a new provider execution as a new external execution record, with a
  new SimOps Run rather than a migration of terminal state or cleanup history.
- Contract tests should prove that reconciliation never selects a different
  provider from the stored Runtime Binding.

## Non-goals

This note does not choose a Docker client, Kubernetes client, storage schema,
cross-provider artifact-transfer strategy, or an interface shape. It does not
assert that Docker and Kubernetes cannot exchange input artifacts; it only
rules out representing a newly launched workload on another provider as the
same running external execution.
