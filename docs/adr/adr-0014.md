# Orchestrate SimOps Stop And Cleanup Through One State Transition Seam

| Field | Value |
| --- | --- |
| Document ID | ADR-0014 |
| Revision | 1.0 |
| Status | Accepted |
| Owner | Software |
| Baseline | SimOps authoritative state hierarchy |

## Status

Accepted

## Context

The SimOps controller currently coordinates runtime stop, runtime cleanup,
legacy lifecycle writes, worker updates, and publication. This makes stop and
cleanup aggregate state a property of controller ordering rather than the
authoritative Run hierarchy. It also makes it easy to conflate absence after
cleanup with proof that execution never occurred.

The Run state model distinguishes lifecycle phase, active execution,
operational condition with evidence, cleanup aggregate, launch disposition,
and derived failure stage. Stop and cleanup must move those facts together in
both the in-memory and Postgres adapters.

## Decision

`SimopsStopOrchestrator` is the sole module that coordinates a stop request.
Its external interface is `Stop(ctx, runID) (SimopsStopOutcome, error)`.
`SimopsController.StopRun` is an HTTP adapter: it delegates to the module and
maps its outcome or error to HTTP; it does not write lifecycle or cleanup
state itself.

The module depends on two adapters:

- `SimopsSpooler` performs runtime stop and cleanup work only.
- An internal `SimopsStopLedger` seam persists typed stop transitions.

The ledger applies one transition atomically: normalized current state,
append-only cleanup attempt or degradation evidence, derived Run aggregate,
and publication intent. Its implementation owns transaction ordering; its
callers do not perform a worker-update loop.

The state order is: persist stop requested and `cleanup=requested`; execute
stop and persist its fact; persist `cleanup=in_progress`; execute cleanup;
then persist completed, incomplete, or failed cleanup. A confirmed stop
failure derives failure stage `stop`; confirmed cleanup failure derives
`cleanup`. An uncertain or partial cleanup is `incomplete` with named
evidence. Cleanup absence is never evidence that a worker did not execute.

Reads render persisted facts only. Evaluating an expired launch-observation
deadline remains the scheduled-policy work reserved for Issue #215.

## Consequences

The controller has one small interface to learn, while execution ordering,
partial outcomes, evidence, aggregate derivation, and outbox consistency gain
locality in one deep module. In-memory and Postgres ledger adapters must pass
the same stop/cleanup contract cases. The spooler must provide enough outcome
detail to avoid inventing per-worker cleanup success from a batch failure.
